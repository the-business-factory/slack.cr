## Findings, ordered by severity and impact

### 1. Medium — Recheck conditional submit before serializing a mutable modal

Evidence: [modal.cr:8–19](../src/slack/ui/surfaces/modal.cr#L8) makes submit
nullable and checks the Input condition only during initialization;
[modal.cr:22–28](../src/slack/ui/surfaces/modal.cr#L22) serializes without that
check. [ViewsOpen.result:12–13](../src/slack/api/endpoints/views_open.cr#L12)
sends the serialized value, including when called through `call`.

A caller can build a valid display modal and then add an Input to its retained
blocks array. The request holds the same array even if the request was already
constructed. It sends an Input without submit. A form modal can also acquire this
state through the newly nullable `submit=` setter:

```crystal
alias M = Slack::UI::Modal
section = Slack::UI::Components::TextSection.render("Details")
input = Slack::UI::Components::InputElement.render("notes", "Notes", "Type here")
blocks = [section] of Slack::TypeAliases::ModalBlock
modal = M.new(title: M::Title.new("Details"), blocks: blocks)
request = Slack::Api::ViewsOpen.new(
  token: "synthetic", trigger_id: "trigger", view: modal
)
blocks << input
request.result # Sends Input with no submit.
```

An offline WebMock probe captured `input=true, submit=false` and one request
through `result`. A separate form with `form.submit = nil` sent the same invalid
shape through `call`. Both probes completed successfully because the stub returned
success. Slack requires submit whenever the view contains an Input block.
[Slack modal reference](https://docs.slack.dev/reference/views/modal-views/)

Required revision: share the conditional-submit check with the serialization or
pre-transport boundary, so retained array changes and setter changes fail with
`InvalidUIBlock` before HTTP. Keep the legacy setters; an immutable tree or checked
endpoint is not required for this repair. Add observable zero-request regressions
for both mutation routes, using `result` and `call`, and retain the valid display
and form cases.

This is a new invalid state enabled by optional submit. It is distinct from the
pre-existing general lack of legacy snapshot guarantees. The Phase 1 statement
that setters remain mutable does not require sending this invalid state.

### 2. Medium — Preserve valid positional Actions and Modal constructors

Evidence: [actions.cr:9](../src/slack/ui/blocks/actions.cr#L9) replaces the
generated constructor with an elements-first constructor. In
[modal.cr:8–12](../src/slack/ui/surfaces/modal.cr#L8), making close and submit
optional changes the order generated by
[initializer_macros.cr:55–75](../src/slack/mixins/initializer_macros.cr#L55).
That macro sorts fields by name and moves required parameters before defaults.

The following valid calls compiled, executed, and produced the expected JSON
against the base source extracted into an OS temporary directory. The identical
calls fail to compile against Phase 1:

```crystal
alias B = Slack::UI::BlockElements::Button
alias M = Slack::UI::Modal
button = B.new(action_id: "go", text: B::Text.new("Go"))
Slack::UI::Blocks::Actions.new("controls", [button]).to_json

blocks = [Slack::UI::Components::TextSection.render("Details")] of Slack::TypeAliases::ModalBlock
M.new(blocks, M::Close.new("Cancel"), M::Submit.new("Save"),
  M::Title.new("Details")).to_json
```

| Type | Base positional order | Phase 1 positional order / failure |
| --- | --- | --- |
| Actions | `block_id, elements` | `elements, block_id`; argument 1 rejects `String`. |
| Modal | `blocks, close, submit, title` | `blocks, title, close, submit`; argument 2 rejects `Modal::Close`. |

The old Actions call with nil block ID and a valid elements array is affected as
well. These calls do not use any malformed values that Phase 1 intentionally
rejects. They contradict the compatibility promise in
[block-kit-phase-1.md:35–40](block-kit-phase-1.md#L35).

Required revision: retain the former valid positional forms with narrow
compatibility overloads that delegate to the validated implementation. Keep the
new named optional-modal form and required Actions elements. Do not change the
global initializer macro. Add compile-and-serialize regressions for both old
forms, including an omitted Actions block ID, alongside the named forms.

The modal helper itself is compatible: the retained six-positional-argument test
passes, and an additional executed probe of the old six-named-argument call
reached the correct WebMock request. That helper test does not cover direct Modal
construction.

### 3. Medium — Validate the Section block ID that now reaches Slack

Evidence: [section.cr:43](../src/slack/ui/blocks/section.cr#L43) starts emitting
`block_id`, but [section.cr:12–28](../src/slack/ui/blocks/section.cr#L12) does not
check its length. The new regression at
[section_spec.cr:63–73](../spec/ui/blocks/section_spec.cr#L63) checks presence and
omission only.

`Section.new(text: Section::Text.new("Details"), block_id: "x" * 256)` constructs
and serializes successfully. An executed probe measured 256 characters in the
emitted ID. Previously this value was dropped; Phase 1 now sends it as part of the
payload. Slack limits Section block IDs to 255 characters.
[Slack Section reference](https://docs.slack.dev/reference/block-kit/blocks/section-block/)

Required revision: reject supplied IDs above 255 characters with `InvalidUIBlock`
before they reach HTTP, including an overlong ID assigned through the retained
setter. Add 254/255/256-character and nil cases, with a Unicode case to establish
character counting. Preserve serialization of valid supplied IDs. This requires
the local bound for the newly emitted field, not layout-wide ID uniqueness or a
general validation framework.

## Verified behavior and intentional Phase 1 limits

- Actions accepts 1 through 25 buttons and rejects nil, empty, and 26-element
  construction. The 25-element maximum matches the
  [Slack Actions reference](https://docs.slack.dev/reference/block-kit/blocks/actions-block/).
  The existing Button-only child type remains explicitly partial.
- Section's supplied empty fields array is rejected, including when text exists.
  Text-only, fields-only, and combined construction remain covered. Non-empty
  text content and broader legacy text validation are still incomplete; the
  shared checked text types belong to later phases.
- Modal labels use the correct 24-character maximum, with a Unicode regression.
  Named display construction omits submit and close. Initial form construction
  requires submit. Optional close and submit reach the helper's structured `view`
  JSON correctly. Finding 1 covers the later mutation gap.
- PlainTextInput checks minimum 0–3000, maximum 1–3000, and minimum not exceeding
  maximum. False and zero remain present; absent optionals are omitted. These
  numeric bounds match the
  [Slack input reference](https://docs.slack.dev/reference/block-kit/block-elements/plain-text-input-element/).
  A paired base/Phase 1 execution also accepted existing `Int8` minimum and
  `Int16` maximum variables, so the storage widening is not a demonstrated
  constructor regression.
- Button uses explicit `primary` and `danger` strings. Dispatch configuration
  emits the specified one- or two-string trigger arrays. Both constructors reject
  unnamed enum values with `InvalidUIBlock`. Additional mutation probes showed
  that wire conversion also rejects unnamed values assigned after construction;
  the Button request failed before transport. These strings match the
  [Button reference](https://docs.slack.dev/reference/block-kit/block-elements/button-element/)
  and [dispatch reference](https://docs.slack.dev/reference/block-kit/composition-objects/dispatch-action-configuration-object/).
- JSON deserialization is inherited, but direct `from_json` probes for Actions,
  Section, Modal, and PlainTextInput fail to compile on both base and Phase 1.
  The failures are concrete nested-parser or abstract-type failures, not missing
  dependencies. For example, Modal cannot construct its Title from a pull parser,
  and Section attempts to instantiate abstract BlockElement. These are existing
  unsupported import paths, not evidence of a new successful validation bypass.
  The retained Phase 0 request-deserialization compile contracts also pass.
- Legacy setters, caller-owned arrays, broad child aliases, mutable text
  discriminators, incomplete field limits, missing surface-wide constraints, and
  unsupported inbound parsing remain outside checked-API guarantees. Existing
  Actions/Section collection mutation and PlainTextInput bound mutation can still
  evade their constructor checks. This review does not require a general snapshot
  or validation migration in Phase 1. The two newly exposed wire defects above
  need bounded repairs within the current API.
- The manifest keeps public implementations partial and placeholders unsupported;
  it does not certify a complete Slack catalog. Its repair claims need to be read
  with the findings above. Phase 0 proof types remain under test support. No new
  builders, checked public types, endpoint replacement, catalog expansion, or
  Phase 2 scope leakage was found. Concrete legacy helper return types remain
  unchanged, consistent with the Phase 0 decisions.

### Finding 1 — Accepted and resolved

Slack requires `submit` when a modal contains an Input block. The legacy Modal
still exposes mutable setters and retains the caller's blocks array, so checking
only during construction was insufficient.

`Modal#to_json` now calls the same private conditional-submit check used during
construction. `ViewsOpen#result` materializes the complete request body before
calling `ApiClient#post`, which makes that recheck an explicit pre-transport
step. `call` continues to use `result`, so it has the same boundary.

`spec/api/views_open_spec.cr` proves both invalid mutation routes with WebMock:
a retained blocks array gains an Input before `result`, and a form modal loses
submit through its setter before a request uses it and calls `call`. Both raise
`InvalidUIBlock` with zero requests. Paired valid display/result and form/call
examples each send one structured request.

Crystal struct value semantics mean changing the original Modal after it is
already copied into a `ViewsOpen` request does not mutate that request. The
retained array does remain shared. This detail narrows the setter reproduction,
but does not change the finding: a setter-mutated Modal was previously accepted
by a newly constructed request and is now rejected before HTTP.

### Finding 2 — Accepted and resolved

The base `properties_with_initializer` declarations and alphabetical macro
ordering establish `block_id, elements` for Actions and
`blocks, close, submit, title` for Modal. Phase 1 changed both positional forms
while its named forms remained valid.

Actions now has a narrow compatibility initializer with the former positional
order and delegates to the same required-elements and size validation. Modal has
a narrow four-argument compatibility initializer with the former types and order

names avoid ambiguity with current named construction. Regressions serialize
both Actions forms, including nil block ID, and the former direct Modal form;
the existing named and optional-label tests remain green.

### Finding 3 — Accepted and resolved

Slack limits a Section `block_id` to 255 characters. Section now checks supplied

The Section regressions cover 254, 255, and 256 characters, nil omission, valid
